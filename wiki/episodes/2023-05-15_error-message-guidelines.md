# Error-Message Guidelines

## Summary

Error messages are critical components of usable experiences that help users recover from mistakes. Effective error messages follow three main categories of guidelines: visibility (displaying errors prominently near their source with accessible indicators), communication (using plain language to clearly describe problems and offer constructive solutions without blaming users), and efficiency (preserving user input, reducing correction effort, and preventing common mistakes). In rare catastrophic failures with no recovery path, novelty and humility may help salvage the experience. Poor error-message design is common because teams focus on the ideal user path rather than thoughtfully addressing deviations.

## Key Takeaways

- **Display errors near their source** — Place error indicators adjacent to problem fields to reduce cognitive load through proximity and help users associate messages with specific elements.
- **Use multiple redundant indicators** — Combine color, text, icons, and animations while remembering that color alone is insufficient for users with color-vision deficiencies.
- **Avoid premature errors** — Don't show errors on exploratory interactions like unfocused text fields; instead use inline, real-time errors for genuinely error-prone situations.
- **Write in human-readable language** — Avoid jargon and technical error codes; use plain language that matches users' mental models, not system implementation details.
- **Offer constructive solutions** — Don't just state the problem; provide guidance or suggested remedies to help users understand how to correct issues.
- **Take a positive tone** — Avoid blame-oriented phrasing like invalid or incorrect; focus on what's needed rather than what users did wrong.

## Quotes

> Effectively handling errors is crucial because it's one of the 5 quality components of usable experiences.

> Error messages should be plainspoken using legible and readable text (many writing apps can give you feedback on a message's readability).

> The proper usage of any system lies with its creators and not with the system's users, so the system must gracefully adapt and not shift blame.
